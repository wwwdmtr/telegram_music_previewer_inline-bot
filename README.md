# 🎵 Music Inline Bot

Инлайн-бот для Telegram в духе `@pic`, только ищет музыку: пишете в любом чате
`@ваш_бот radiohead creep` — получаете список треков и отправляете выбранный
как аудио-сообщение.

Источники — **Deezer** (основной) и **iTunes Search API** (фолбэк). Оба публичные,
без ключей и регистрации. Отдают 30-секундные превью — это всё, что доступно
через открытые API; полных треков не даст ни один из них.

## Быстрый старт

```bash
cp .env.example .env          # вставьте BOT_TOKEN от @BotFather
docker compose up -d --build
docker compose logs -f bot
```

Поднимается один контейнер, кэш живёт в памяти процесса — этого достаточно для
одной реплики. Нужен общий кэш на несколько реплик — добавьте оверлей с Redis:

```bash
docker compose -f docker-compose.yml -f docker-compose.redis.yml up -d --build
```

Перед первым запуском в **@BotFather**: `/setinline` → выбрать бота → задать
placeholder. Без этого инлайн-режим не включится. Рекомендуемый текст:

```
исполнитель и название
```

Плейсхолдер — это серая подсказка в поле ввода после `@имя_бота`, её видит
пользователь до того, как начнёт печатать, так что она должна описывать формат
запроса (см. ниже), а не бота.

## Формат запроса

Обычный текст, никакого синтаксиса. Проверено на живом Deezer:

| Запрос | Результат |
|---|---|
| `radiohead creep` | Radiohead — Creep |
| `creep radiohead` | то же — порядок слов не важен |
| `Radiohead - Creep`, `Radiohead — Creep` | то же — дефисы и тире не мешают |
| `creep` | то же — одного названия достаточно |
| `AC/DC Thunderstruck`, `Guns N' Roses Sweet Child O Mine` | работают: слеши и апострофы не ломают поиск |
| `Кино Группа крови` | работает — кириллица ищется, если так записано в каталоге |
| *(пусто)* | текущий чарт |

Что **не** работает:

- **Синтаксис `artist:` / `track:`.** Deezer его документирует, но на публичном
  эндпоинте он сломан: `artist:"radiohead"` возвращает 0 результатов, а обычное
  `radiohead` — находит. Поэтому `:` и кавычки вырезаются из запроса, а поиск
  идёт по свободному тексту.
- **Кириллица для исполнителей, записанных латиницей.** `артик и асти` → 0
  результатов, `artik asti` → находит Artik & Asti. Подсказка про это есть в
  сообщении «ничего не найдено».
- **Переведённые названия.** `счётные звёзды` → 0, `counting stars` → находит.

Технические границы: меньше `MIN_QUERY_LENGTH` (по умолчанию 2) символов —
запрос к API не уходит вообще; длиннее 100 символов — обрезается (Telegram и так
ограничивает инлайн-запрос 256 символами); регистр и лишние пробелы
нормализуются, так что `  MASSIVE   ATTACK ` и `massive attack` — один и тот же
запрос и один ключ кэша.

### Деплой на VPS

Инструкция под Dokploy — в [DEPLOY.md](DEPLOY.md). Коротко: тип приложения
**Application** с билдером **Dockerfile**, домен и порты не нужны (бот работает
через long polling), `BOT_TOKEN` задаётся в Environment панели, а не файлом.
Главное — не держать второй polling-инстанс на том же токене.

### Рядом с другими проектами на том же VPS

Отдельный Docker не нужен — один демон держит контейнеры всех проектов. Этот
compose к соседям не лезет:

- `name: music-inline-bot` — своё имя проекта, свои сеть и контейнеры, даже если
  папки называются одинаково;
- ни один порт не публикуется (бот сам стучится в Telegram по long polling), так
  что занятые на хосте порты не мешают;
- `docker compose up -d` здесь не трогает контейнеры других проектов;
- логи ротируются (`max-size 10m`, 3 файла) — общий диск не забьётся.

#### Нужен ли Redis, если он уже есть для другого проекта

По умолчанию **нет**: бот его не использует вообще. `docker compose up -d`
поднимает один контейнер с кэшем в памяти процесса, чужой Redis при этом не
трогается и второй не появляется. Redis нужен ровно в одном случае — когда
копий бота больше одной и кэш должен быть общим.

Если этот момент настанет, вариантов два.

**Свой контейнер (рекомендуется).** Оверлей `docker-compose.redis.yml`. Два
Redis на одном VPS друг другу не мешают: разные контейнеры, разные сети, порт
6379 наружу не публикуется ни здесь, ни (скорее всего) там — конфликт возможен
только если оба пробрасывают порт на хост. Цена — ~8 МБ памяти.

**Подключиться к существующему.** Нужно попасть в его сеть и занять свободный
номер базы (`/1`, `/2`, …), чтобы ключи не смешались с чужими:

```bash
docker network ls          # найти сеть чужого проекта, напр. other_default
```

```yaml
# docker-compose.external-redis.yml
services:
  bot:
    environment:
      CACHE_BACKEND: redis
      REDIS_URL: redis://redis:6379/1   # redis = имя сервиса в чужой сети
    networks: [default, other_default]
networks:
  other_default:
    external: true
```

```bash
docker compose -f docker-compose.yml -f docker-compose.external-redis.yml up -d
```

Ключи бота и так живут под префиксом `music:`, так что даже в общей базе они
различимы. Но если в том Redis лежат не только кэш-данные (сессии, очереди),
общий инстанс — плохая идея: при упоре в `maxmemory` политика вытеснения
начнёт выбрасывать чужие ключи.

## Как это работает

```
inline_query
    │
    ├─ len(query) < 2 ──────────────────────────► пустой ответ + подсказка-кнопка
    │
    ├─ query == "" ────────────────────────────► чарт Deezer
    │
    ▼
SearchService
    │
    ├─ 1. кэш свежий (< 5 мин)? ──────────────► отдаём сразу
    │
    ├─ 2. single-flight: тот же запрос уже
    │     в полёте? ──────────────────────────► ждём тот же результат
    │
    ├─ 3. провайдеры по очереди, каждый под
    │     своим token bucket и таймаутом 2 с
    │     Deezer → iTunes
    │
    ├─ 4. всё упало, но есть протухшая
    │     запись (< 30 мин)? ─────────────────► отдаём её (stale-on-error)
    │
    └─ 5. и этого нет ───────────────────────► «Сервис недоступен», cache_time=5
```

### Три слоя кэша

| Слой | TTL | Что даёт |
|---|---|---|
| Кэш Telegram (`cache_time` в `answerInlineQuery`) | 300 с | Одинаковый запрос от других пользователей **вообще не долетает до бота**. Работает, потому что результаты не персональные → `is_personal=false`. |
| Наш кэш (memory или Redis) | 300 с «свежести» | Повторный запрос не идёт в Deezer. Ключ — `s:{нормализованный запрос}:{offset}:{page_size}`. |
| Тот же кэш как аварийный запас | ещё 1500 с | Если все провайдеры лежат, лучше отдать ответ пятиминутной давности, чем пустой список. |

Реализация: в хранилище запись живёт `CACHE_STALE_TTL` (жёсткое вытеснение),
а «свежесть» считается по `created_at` в самой записи. Один TTL на уровне
хранилища, два состояния на уровне логики.

**Негативное кэширование**: пустой результат кэшируется на тех же условиях —
иначе популярная опечатка будет долбить апстрим на каждое нажатие клавиши.

**Single-flight**: если десять человек одновременно набрали одно и то же, к
Deezer уйдёт один запрос, остальные дождутся его результата. Ожидание обёрнуто
в `asyncio.shield`, чтобы отменённый инлайн-запрос (пользователь продолжил
печатать) не убивал общий поход в апстрим.

**Redis vs memory**: `memory` (cachetools.TTLCache) — для одной реплики,
`redis` — если реплик несколько, иначе у каждой будет свой кэш и hit-rate
упадёт кратно. Разница только в бэкенде, логика кэша одна и та же. Redis в
оверлее поднят как чистый кэш: без персистентности, `maxmemory 256mb`,
`allkeys-lru`. Недоступный Redis не ломает поиск — ошибки чтения и записи
логируются и трактуются как промах.

### Почему боты «подвисают» и что сделано здесь

Типичные причины, по которым телеграм-бот отвечает через несколько секунд:

1. **Последовательная обработка апдейтов.** Один медленный хендлер задерживает
   всю очередь. В aiogram 3 этого нет: `handle_as_tasks=True` по умолчанию, на
   каждый апдейт создаётся отдельная задача.
2. **Блокирующие вызовы в event loop** — `requests`, `time.sleep`, синхронный
   файловый ввод-вывод. Один такой вызов останавливает *всех* пользователей.
3. **Складывающиеся таймауты.** Самая частая скрытая причина: таймаут на запрос
   × число попыток × число фолбэков. Здесь было до 8 секунд (ожидание лимитера
   2 с + HTTP 2 с, и так для каждого из двух провайдеров) — теперь есть общий
   потолок `SEARCH_TIMEOUT`.
4. **Отсутствие таймаута вообще** — запрос к внешнему API может висеть минутами.
5. **Отправка файла по URL.** Telegram сам скачивает файл со стороннего CDN,
   когда пользователь тапнул результат. Это вне нашего контроля и выглядит как
   «отправляется…». Лечится `InlineQueryResultCachedAudio`: превью один раз
   загружается в служебный чат, дальше отдаётся `file_id` — отправка мгновенная.
   Не реализовано.
6. **Флуд-лимиты Telegram.** На 429 с `retry_after` наивный бот засыпает и
   выглядит зависшим.

Замерено на живых запросах:

| Проверка | Результат |
|---|---|
| Два намертво зависших провайдера | обрыв за 4.01 с, дальше stale-кэш или сообщение об ошибке |
| 20 разных запросов одновременно | 1.46 с (последовательно было бы ~8 с) |
| Медленный запрос рядом с быстрым | быстрый ответил за 0.20 с, медленный продолжал висеть |
| Задержка тика event loop под нагрузкой | максимум 24 мс, ни одного тика >50 мс |

Блокирующих вызовов в коде нет: HTTP — `httpx.AsyncClient`, Redis —
`redis.asyncio`, ожидания — `asyncio.sleep`, блокировки — `asyncio.Lock`.
Из синхронного только CPU-мелочь: sha1 для id результата и регулярки дедупа.

### Антифлуд

Две поверхности с разной формой трафика, поэтому лимиты раздельные
(`outer_middleware`, то есть до фильтров — отброшенный апдейт не стоит ничего):

| | Лимит по умолчанию | Что при превышении |
|---|---|---|
| Инлайн-запросы | burst 10, +2/с | Апдейт отбрасывается молча. Одно нажатие без результата незаметнее строки с ошибкой, следующее проходит |
| Сообщения в личке | burst 5, +0.5/с | Одно предупреждение за период остывания, не на каждое сообщение |

Счётчики на пользователя живут в `TTLCache` — ограничены по размеру
(`THROTTLE_MAX_USERS`) и забываются после 10 минут простоя, так что поток
запросов с разных id не может съесть память. Админы из `ADMIN_IDS` под лимит не
попадают, чтобы `/stats` работал во время флуда. Отброшенное видно в `/stats`.

| Случай | Поведение |
|---|---|
| Ничего не найдено | Одна видимая строка-объяснение (`InlineQueryResultArticle`) + кнопка «как искать» в личку. Пустой список некоторые клиенты просто не показывают. |
| Пустой запрос | Чарт Deezer вместо пустоты. |
| Запрос короче 2 символов | Отвечаем без обращения к API. |
| Конец пагинации | Пустой ответ **без** «ничего не найдено» — на второй странице это просто конец списка. |
| Мусор в `offset` | Приводим к 0, зажимаем сверху 500. |
| Трек без превью (регион-лок) | Отфильтровывается в провайдере — Telegram не смог бы его проиграть. |
| Дубликаты (сборники, ремастеры, `feat.`) | Дедуп по нормализованной паре (исполнитель, название). |
| Deezer вернул `ExceedingLimit` | `ProviderRateLimited` → сразу переход к iTunes. |
| Deezer недоступен / таймаут | То же: следующий провайдер, потом stale-кэш. |
| Все провайдеры легли | Понятное сообщение, `cache_time=5` — чтобы Telegram не заморозил ошибку на 5 минут. |
| Explicit | Помечается 🔞 в заголовке, не фильтруется. |
| Свой rate limit | Token bucket на провайдера: Deezer 8 rps (лимит ~50/5 с на IP), iTunes 0.3 rps (~20/мин). |
| Падение парсера | Ловится как обычная ошибка провайдера, бот продолжает работать. |
| Апдейты, накопившиеся за простой | `drop_pending_updates=True` — просроченные `inline_query` всё равно нельзя ответить. |

### Что можно менять в ответе

Telegram даёт менять у аудио-результата ровно четыре вещи, и все они вынесены в
настройки или в один небольшой модуль `render.py`:

| Элемент | Где | Как поменять |
|---|---|---|
| Кнопка «Открыть в Deezer» | под отправленным треком | `SHOW_SOURCE_BUTTON=false` |
| Подпись | под отправленным треком | `CAPTION_STYLE=full\|short\|none` |
| Название и исполнитель | строка в списке **и** плеер | `render.audio_result` |
| Текст строк «ничего не найдено» / «сервис недоступен» | список | `handlers/inline.py` |

`CAPTION_STYLE=none` даёт самый «чистый» вид: только плеер, без текста под ним —
название и исполнитель всё равно видны, они приходят из полей `title` и
`performer` самого результата, а не из подписи.

Чего поменять нельзя: обложку в выпадающем списке (у `InlineQueryResultAudio`
нет поля для картинки) и длину превью — 30 секунд задаёт источник.

### Тонкости Telegram Bot API

- **`audio_duration = 30`**, а не длина трека: Telegram описывает файл, на
  который мы ссылаемся, а это 30-секундное превью. Полная длительность уходит
  в подпись.
- **У `InlineQueryResultAudio` нет поля с картинкой.** В отличие от `@pic`,
  обложку в выпадающем списке показать нельзя — Telegram рисует свою иконку
  аудио. Обложка остаётся полезной в article-строках.
- **`id` результата ≤ 64 байт** → sha1 от `провайдер:id`.
- **`next_offset` растёт на `page_size`**, а не на число оставшихся после
  дедупа строк: это индекс в апстриме, иначе пагинация начнёт пропускать треки.
- `switch_pm_text` устарел с Bot API 7.0 — используется `button`
  (`InlineQueryResultsButton`).

## Неинлайн-поведение

Главная функция бота живёт в инлайн-режиме, а его пользователи сами не находят.
Поэтому все остальные поверхности существуют, чтобы привести туда: под каждым
ответом есть кнопки **«🔎 Попробовать здесь»** (`switch_inline_query_current_chat`)
и **«📨 Выбрать чат»** (`switch_inline_query_chosen_chat`) — они подставляют
`@имя_бота ` прямо в поле ввода нужного чата.

**В личке:**

| Что прислали | Что делает бот |
|---|---|
| `/start`, `/help` | Инструкция с примерами + кнопки перехода в инлайн |
| `/stats` | Hit-rate кэша, ошибки апстрима, разбивка по провайдерам (только `ADMIN_IDS`, остальным молчит) |
| Текст | Лучшее совпадение аудио-сообщением + до 5 альтернатив списком |
| Текст короче 2 символов | Отвечает без обращения к API |
| Стикер, фото, голосовое | Объясняет, что нужен текст (раньше молчал) |
| `/start notfound`, `/start error` | Точки входа для кнопок из инлайн-ответов |

**В группах:**

| Событие | Что делает бот |
|---|---|
| Бота добавили в чат | Короткое приветствие с кнопкой «Попробовать здесь» (раньше — ничего) |
| `/help` в группе | Короткая версия, не стена текста из лички |
| Обычные сообщения | Не читает и не отвечает: privacy mode включён, плюс хендлер текста ограничен приватными чатами |
| Добавили без права писать | Ловит `TelegramForbiddenError` и молчит, это не ошибка |

Меню команд (`/`) заполняется при старте через `setMyCommands`, отдельно для
личек и для групп — до этого пользователь не видел никаких подсказок в
интерфейсе.

### Статистика выбранных треков

`chosen_inline_result` бот логирует, но Telegram **не присылает** эти апдейты,
пока в @BotFather не включён `/setinlinefeedback`. По умолчанию он выключен,
так что отсутствие строк `chosen result=` в логах не означает, что треки не
отправляют — просто обратной связи нет. Включать стоит, если нужна метрика
«сколько показов превратилось в отправку»; на больших объёмах Telegram
рекомендует не 100%, а долю (10%).

| Переменная | По умолчанию | Смысл |

## Диагностика

| Симптом | Причина |
|---|---|
| `Ошибка конфигурации: bot_token: Field required` | Нет `.env` или в нём пустой `BOT_TOKEN`. Выход с кодом 2. |
| `не похоже на токен от @BotFather: внутри значения есть пробел` | В `BOT_TOKEN` попал лишний символ при вставке. Выход с кодом 2. |
| `Telegram отверг токен` | Токен по форме верный, но Telegram его не принял. Выход с кодом 2. |
| Бота добавили в группу, приветствия нет | У бота нет права писать в этом чате — смотрите `cannot post in chat` в логах. |
| Инлайн-режим не срабатывает в чатах | Не выполнен `/setinline` в @BotFather. |
| `redis get failed: ...` в логах, но бот работает | Redis недоступен; поиск продолжает работать без кэша. |
| Ответы кажутся «застывшими» | Это кэш Telegram (`INLINE_CACHE_TIME`), а не бот. Для отладки поставьте 0. |

## Что можно добавить дальше

- **Вебхук вместо polling** — при заметной нагрузке. `aiohttp`-приложение +
  `SimpleRequestHandler` из aiogram, всё остальное не меняется.
- **История запросов** пользователя на пустой запрос вместо чарта (Redis,
  `LPUSH`/`LTRIM` на юзера, `is_personal=true` для таких ответов).
- **Prometheus** вместо `/stats`: hit-rate, латентность апстрима, доля ошибок.
- **Spotify** как источник метаданных (Client Credentials Flow — логин
  пользователя не нужен, но нужны client_id/secret).
